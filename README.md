Демо мен нақты талдаудың айырмасы
Әдепкі DEMO_MODE = true. Таңдалған файлдар оқылмайды және серверге жіберілмейді. Кез келген жүктелген жұп үшін №8 → №9 алдын ала дайындалған сценарий көрсетіледі. Upload scanning, tool кезеңдері, 47 функция, 1 184 байланыс, 96% confidence және Document DNA — демонстрация. DNA ғылыми өлшем емес.

3.4, 3.5 және 5.3.2 тармақтарының үзінділері берілген DOCX файлдарымен тексерілген. «Тесттік» тұжырымдар мен «ДЕМО-…» тармақтары жасанды. Үзінділердің түрі Source Trace пен экспортта белгіленген. Құрылымдағы өзгеріс функцияның ресми ауысқанын өздігінен дәлелдемейді.

Интерфейс операциялар күйін көрсетеді; модельдің ішкі ойлау тізбегін көрсетпейді. Еркін сұрақтарға шынайы жауап және құжаттарды өңдеу команданың backend модулінде орындалуы керек.

Архитектура және backend
index.html  → экран құрылымы, диалогтар, қолжетімділік
style.css   → responsive Command Center, core/orbit/scan анимациялары
script.js   → Canvas, күй, демо, карта, Agent Insight, API, экспорт
                     │
                     ├─ DEMO_MODE=true  → жергілікті сценарий
                     └─ DEMO_MODE=false → Agent API
                          POST /api/documents
                          POST /api/analyze
                          POST /api/agent
                          GET  /api/session/:id
                          GET  /api/evidence/:id
Backend қосу үшін script.js басында DEMO_MODE = false, API_BASE = 'http://127.0.0.1:8000' орнатыңыз. Backend CORS пен файл валидациясын баптауы тиіс. server.cjs — тек статикалық сервер, Agent API емес. API келісімі: docs/integration.md.

Қолдау: PDF, DOCX, XLSX; әр редакцияға бір файл, файл көлемі 20 MB-тан аспайды. Клиент кеңейтімді, көлемді және бос файлды тексереді. Мазмұнды backend тексеруі керек. Сұрауларда 120 секунд таймаут бар. Нақты режимде қате шықса, демо жауабына үнсіз ауыспайды. «Күтуді тоқтату» браузер сұрауын үзеді; сервер тапсырмасын жоюға кепіл емес.

API мәтіндері HTML ретінде орындалмайды. CSV формула префикстері қорғалған. API кілттерін frontend-ке салмаңыз. Сессия күйі жадта ғана сақталады; жаңартқанда жойылады. Нақты режимде Settings арқылы сервердің session_id мәнін енгізіп қалпына келтіруге болады. Google Fonts жүктелмесе жүйелік қаріптер қолданылады.

Деректер ағыны:

Пайдаланушы «дейінгі» және «кейінгі» құжатты жүктейді (немесе кірістірілген тест үлгілерін пайдаланады).
core/parser.py мәтінді алып, тармақтардың нөмірлеуін (1.1, 2.3.4 және т.б.) сақтайды — модельге әр қорытындының нақты дереккөзін көрсету үшін бұл қажет.
core/analyzer.py екі мәтінді де Claude-қа бір сұраныспен жібереді, қатаң жүйелік промпт мыналарды талап етеді:
қайта ұйымдастырылған / сақталған / құрылған бөлімшелерді анықтау;
функционалды салыстырып, функциялардың жоғалуын табу;
функциялардың қайталануын және мүдделер қақтығысының ықтимал жағдайларын табу;
әр қорытынды үшін дереккөзді (құжат + тармақ нөмірі) көрсету;
мәтінмен расталмаған қорытынды жасамау.
Модельдің JSON форматындағы жауабы талданып, app.py-да көрсетіледі: кестелер, дереккөздері бар ашылмалы карточкалар, қорытынды тұжырым.
Орнату және іске қосу
bash

# 2. Виртуалды орта жасау (ұсынылады)

export ANTHROPIC_API_KEY=sk-ant-...     # Windows (PowerShell): $env:ANTHROPIC_API_KEY="sk-ant-..."

Тест сценарийі (тексеру үшін)

data/ қалтасында Ішкі аудит туралы нақты Ереженің екі қысқартылған нұсқасы бар — №8 редакция («дейін») және №9 редакция («кейін»). Олардың арасындағы өзгерістер алдын ала белгілі:

№9 редакцияда екі жаңа департамент пайда болды — ДИТААД және ДОА, олар №8 редакцияда болмаған (онда «Ішкі аудит бағытының директоры» деген жалпылама рөл болған);
5-бөлімнің бірқатар функциялары мен тармақтары жаңа департаменттер арасында қайта тұжырымдалып, қайта бөлінген.

Агент ДИТААД пен ДОА-ны «құрылған», ДНМ мен ДККМ-ны «сақталған» деп белгілеуі және әр қорытындының дереккөзі ретінде нақты тармақтарды (мысалы, 3.4-тармақ, 5.3.2-тармақ) көрсетуі тиіс.

Іске асыру мәртебесі (тапсырмадағы must have)
#	Талап	Мәртебе
1	Қайта ұйымдастырылған/сақталған/құрылған бөлімшелерді анықтау	✅
2	Функционалды салыстыру және функциялардың жоғалуын анықтау	✅
3	Функциялардың қайталануын және мүдделер қақтығысын анықтау	✅
4	Әр қорытынды үшін дереккөзге сілтеме (құжат + тармақ)	✅
5	Түсінікті түрдегі қорытынды аналитикалық тұжырым	✅
MVP-дің белгілі шектеулері және ықтимал дамуы
Салыстыру модельге бір сұраныспен орындалады — құжаттардың үлкен жиынтығында жұмыстың сенімдірек әрі тексерілетін болуы үшін оны жеке қадамдарға бөлген жөн (агенттік pipeline): (1) әр құжаттың құрылымын жеке алу → (2) салыстыру → (3) тармақтарға сілтемелерді жеке тексеру шақыруымен верификациялау.
Сыртқы НҚА/стандарттармен автоматты салыстыру және басқа операторлармен бенчмаркинг жоқ (тапсырманың «Опционально» бөлімін қараңыз) — дамудың келесі қадамы.
Өте үлкен құжаттар (жүздеген бет) үшін толық мәтінді промптқа беру орнына чанкинг пен векторлық іздеу (RAG) қажет болады.
ЖИ қорытындылары ұсынымдық сипатта болады және жауапты қызметкердің тексеруін талап етеді (тапсырманың «Ограничения» бөлімін қараңыз).
