## Backend MVP — команданың құжаттамасы
Hackathon team repository for TheDArk

```text
mvp/
├── app.py                 # Streamlit UI: загрузка документов, отображение результата
├── core/
│   ├── parser.py           # Извлечение текста из .docx / .pdf / .xlsx / .txt
│   └── analyzer.py         # Ядро агента: промпт + вызов Claude API + разбор JSON-ответа
├── data/
│   ├── before_sample.txt   # Тестовый пример "до" (Положение о внутреннем аудите, ред. №8)
│   └── after_sample.txt    # Тестовый пример "после" (ред. №9)
├── requirements.txt
└── .env.example
```

**Поток данных:**
1. Пользователь загружает документ «до» и документ «после» (или использует
   встроенные тестовые примеры).
2. `core/parser.py` извлекает текст, сохраняя нумерацию пунктов (1.1, 2.3.4 и т.д.) —
   она нужна модели, чтобы указывать точный источник каждого вывода.
3. `core/analyzer.py` отправляет оба текста в Claude одним запросом со строгим
   системным промптом, который требует:
   - определить реорганизованные / сохранённые / созданные подразделения;
   - сопоставить функционал и найти потери функций;
   - найти дублирование функций и потенциальный конфликт интересов;
   - для каждого вывода указать источник (документ + номер пункта);
   - не делать выводов, не подтверждённых текстом.
4. Ответ модели в формате JSON парсится и отображается в `app.py`: таблицы,
   раскрывающиеся карточки с источниками, итоговое заключение.

## Известные ограничения MVP и возможное развитие

- Сравнение выполняется **одним запросом к модели** — для более надёжной и
  проверяемой работы на больших комплектах документов стоит разбить на
  отдельные шаги (агентный pipeline): (1) извлечение структуры каждого
  документа отдельно → (2) сопоставление → (3) верификация ссылок на пункты
  отдельным проверочным вызовом.
- Нет автоматического сопоставления с внешними НПА/стандартами и
  бенчмаркинга с другими операторами (см. раздел «Опционально» задачи) —
  следующий шаг развития.
- Для очень больших документов (сотни страниц) потребуется чанкинг и
  векторный поиск (RAG) вместо передачи полного текста в промпт.
- Выводы ИИ носят рекомендательный характер и требуют проверки ответственным
  сотрудником (см. раздел «Ограничения» задачи).

## 1. Жалпы ережелер

- **Жобаның мақсаты:** ұйымды қайта құрылымдау (реорганизация) кезінде ішкі нормативтік құжаттардың (Ережелер, Нұсқаулықтар т.б.) екі редакциясын («дейін» және «кейін») семантикалық әрі функционалдық тұрғыдан автоматты түрде салыстыру, сондай-ақ құжаттармен жұмыс істеуге арналған корпоративтік платформа ұсыну.
- **Негізгі міндеті:** функциялардың жоғалуын, қайталануын, жаңадан пайда болуын, мүдделер қақтығысын анықтау және әрбір тұжырымды құжаттың нақты тармағына байланыстыру (Explainable AI / Source Trace).
- **Қосымша міндеттері:** тіркелмеген қонаққа ЖИ талдауын ашық беру; құжатты өңдеуді тек авторизацияланған пайдаланушыға беру; пайдаланушы деректерін дерекқорда сақтау; құжат үлгілерінің кітапханасы; әрекеттер тарихы.
- **Басты принцип:** барлық рөлдік шешімдерді тек Backend қабылдайды. Frontend тек пайдаланушыға не қолжетімді екенін көрсетеді, қауіпсіздікті қамтамасыз етпейді.

## 3. Жүйе архитектурасы

Жүйе 4 қабаттан тұрады: Frontend, Backend (рөлдерді басқаратын орталық қабат), Core Processing & AI Engine және дерекқор.

### 3.1. Frontend (UI)

- **Технологиялар:** Single Page Application (HTML5, CSS3, Vanilla JS) / Streamlit (MVP үшін).
- **Интерфейс компоненттері:**
  - *Neural Core:* анимациялық өңдеу орталығы.
  - *Document A/B View:* екі құжатты қатар салыстыру аймағы.
  - *Source Trace & Agent Insight:* агенттің қорытындысы мен нақты тармақтарға сілтеме беретін модуль.
  - *Command Line (Ctrl+K):* жедел командалар диалогы («Үлгілерді ашу», «Тарихты ашу», «Жаңа құжат»).
  - *Кіру, тіркелу беттері және профиль.*
  - *Құжат редакторы* (тек авторизацияланғандарға).
  - *Үлгілер кітапханасы* және *Тарих* беттері.
  - *Әкімші панелі* (тек `admin` рөліне).
- Рөлге қолжетімсіз элементтер жасырылады немесе «құлыптанған» белгісімен көрсетіледі. Қонаққа ЖИ талдауынан кейін «Нәтижені сақтау, құжатты өңдеу және экспорттау үшін кіріңіз» ұсынысы шығады.
- Токендер frontend-те тек HttpOnly cookie арқылы өңделеді.

### 3.2. Backend (API Server)

- **Технологиялар:** Node.js (REST API) немесе Python (FastAPI). Архитектура: модульді монолит, әр модуль жеке қызмет ретінде бөлінуге дайын.
- **Backend модульдері:**

| Модуль | Міндеті |
|---|---|
| Auth Service | Тіркеу, кіру, шығу, токендер, email растау, құпиясөзді қалпына келтіру, SSO |
| Access Control (RBAC) | Рөл мен рұқсаттарды тексеру, ресурс иелігін тексеру, квоталар |
| Document Service | Құжаттарды жүктеу, сақтау, редакциялау, нұсқалау |
| Template Service | Құжат үлгілерінің кітапханасы, үлгі бойынша құжат жасау |
| Analysis Service | ЖИ талдауын іске қосу, нәтижені сақтау, дәлелдемелер (evidence) |
| History & Audit Service | Пайдаланушы тарихы және жүйелік әрекеттер журналы |
| Admin Service | Пайдаланушылар, рөлдер, үлгілер, лимиттер, статистика |

### 3.3. Backend-тің рөлдік қызметі (Access Control)

Барлық API сұранысы төмендегі тізбектен өтеді:

1. **Идентификация:** access-токен тексеріледі; токен жоқ болса, сұраныс `guest` ретінде өңделеді.
2. **Рөлді анықтау:** рөл токеннен емес, дерекқордан (қысқа мерзімді кэшпен, ең көбі 60 секунд) алынады. Рөл өзгергенде немесе пайдаланушы бұғатталғанда токен нұсқасы (`token_version`) өседі және ескі токендер жарамсыз болады.
3. **Рұқсатты тексеру:** әр эндпоинт қажетті рұқсатты (permission) көрсетеді, ал рөл-рұқсат кестесі (`role_permissions`) дерекқорда сақталады.
4. **Ресурс саясаты:** пайдаланушы тек өз құжаттарына, талдауларына және тарихына қол жеткізеді (иелікті тексеру). Өзгенің ресурсына сұраныс `404` қайтарады, бұл ресурстың болуын жасырады.
5. **Квоталар:** қонаққа IP бойынша, тіркелгенге пайдаланушы бойынша ЖИ сұраулары лимиті қойылады.
6. **Өңдеу:** бизнес-логика орындалады.
7. **Аудит:** маңызды әрекет `activity_log` кестесіне жазылады.

Қате кодтары: `401` (кіру қажет), `403` (рұқсат жоқ), `404` (ресурс жоқ немесе қолжетімсіз), `429` (лимит асылды).

### 3.4. Core Processing & AI Engine

- **Parser (`core/parser.py`):** `.pdf`, `.docx`, `.xlsx`, `.txt` форматтарынан мәтінді оның тармақтық нумерациясын (1.1, 2.3 т.б.) сақтай отырып алу.
- **Analyzer (`core/analyzer.py`):** Anthropic Claude API / OpenAI API интеграциясы. Арнайы жүйелік промпт арқылы құрылымдалған JSON жауабын алу. API кілттері тек серверде сақталады.

### 4.1. Қонақ режимінің ережелері

- Тіркелусіз құжат жүктеп, ЖИ талдауын алуға болады.
- Талдау нәтижесі экранда көрсетіледі, бірақ дерекқорға сақталмайды және тарихқа түспейді.
- Қонақтың жүктеген файлдары талдаудан кейін серверден автоматты түрде жойылады.
- Құжатты редакциялау, үлгілерді қолдану, экспорттау және сақтау — тек авторизациядан кейін. Backend қонақтың мұндай сұранысына `401` қайтарады.
- Теріс пайдаланудан қорғау: бір IP-ден тәулігіне ең көбі 5 талдау (мән конфигурацияланады).

### 4.2. Тіркелген пайдаланушы және қызметкер

- Барлық талдаулар, құжаттар мен өзгерістер дерекқорға сақталады.
- Қызметкерге қосымша: корпоративтік үлгілер, құжатпен бөлісу, ішкі санаттар.
- Қызметкер мәртебесі корпоративтік email домені, SSO немесе әкімшінің қолмен растауы арқылы беріледі.

### 4.3. Әкімші

- Пайдаланушыларды растау, бұғаттау, рөлін өзгерту.
- Құжат үлгілері каталогын басқару.
- Жүйелік журналды, ЖИ шығындары мен лимиттер статистикасын көру.

## 5. Функционалдық талаптар

### 5.1. Файлдарды өңдеу

- Сүйреп апару (Drag-and-Drop) арқылы PDF, DOCX, XLSX (және TXT) файлдарын қабылдау.
- Файл көлемін тексеру (максимум 20 MB) және форматты клиент тарапынан да, серверде де валидациялау (MIME түрі бойынша).
- Жүктелген файлдарға вирус және макрос тексеруі жүргізіледі.

### 5.2. Құрылымдық және семантикалық талдау (AI Analyzer)

- **Құрылымдық өзгерістер:** жаңадан құрылған, сақталған, жойылған немесе біріктірілген департаменттер мен бөлімшелерді анықтау.
- **Функцияларды сәйкестендіру:** қайта тұжырымдалған функцияларды бір-бірімен сәйкестендіру (Matrix Mapping).
- **Қауіптерді анықтау:**
  - *Lost Functions:* басқа бөлімге берілмей, мүлдем жоғалған функциялар.
  - *Overlaps / Conflict of Interest:* екі немесе одан да көп бөлімге бірдей функцияның жүктелуі немесе бақылаушы мен орындаушы функцияларының қайталануы.
- Ұзақ талдау асинхронды орындалады (кезек), статусы көрсетіледі, нәтиже `analyses` кестесіне сақталады (тіркелгендер үшін).

### 5.3. Дереккөзді бақылау (Source Trace / Explainability)

- Агент шығарған әрбір қорытынды үшін «A құжаты, X тармағы» ↔ «B құжаты, Y тармағы» түріндегі дәлелді сілтемелерді ұсыну.
- Сілтеме басылғанда Document A/B View екі құжаттағы сәйкес тармақты қатар ашады.

### 5.4. Экспорттау және есептілік

- Талдау нәтижелерін JSON, CSV және PDF (басып шығаруға бейімделген) форматтарында экспорттау. Экспорт тек авторизацияланған пайдаланушыға қолжетімді.
- CSV экспортында формулаларды енгізуден қорғау (Formula Prefix Protection).

### 5.5. Тіркеу және авторизация (Auth Service)

1. Тіркеу: email, құпиясөз, аты-жөні; қызметкер үшін қосымша бөлім және лауазым.
2. Кіру (login) және шығу (logout).
3. Email растау және құпиясөзді email арқылы қалпына келтіру.
4. Қосымша: корпоративтік SSO (OAuth2 / OpenID Connect / LDAP).
5. Токен механизмі: қысқа мерзімді JWT access-токен және refresh-токен (HttpOnly, Secure cookie), refresh-токен айналымымен (rotation).
6. Құпиясөздер дерекқорда тек хэш түрінде сақталады (bcrypt немесе Argon2). Құпиясөз талабы: кемінде 8 таңба, әріп пен сан.
7. Брутфорстан қорғау: қате кіру әрекеттерін шектеу (rate limiting), уақытша бұғаттау.
8. Барлық қорғалған эндпоинттерде рөл мен рұқсат серверде тексеріледі (3.3 бөлімі).

### 5.6. Құжат үлгілері (Template Library)

Компания қызметінде қолданылатын кез келген құжаттың үлгілері каталогта болады.

- **Санаттар:** ішкі нормативтік құжаттар (Ереже, Нұсқаулық, Регламент, Саясат); ұйымдастырушылық-өкімдік құжаттар (Бұйрық, Өкім, Хаттама, Шешім); кадрлық құжаттар (Өтініш, Лауазымдық нұсқаулық, Еңбек шарты, Қызметтік жазба); шарттар мен келісімдер (Қызмет көрсету шарты, NDA); есептілік пен хат алмасу (Қызметтік хат, Баяндама хат, Есеп, Акт); бөлімше туралы ереже және функциялар матрицасы үлгілері.
- Санат, іздеу және сүзгі бойынша каталог, үлгіні алдын ала қарау (preview).
- «Үлгі бойынша құжат жасау»: үлгінің көшірмесі пайдаланушының жеке құжаты ретінде сақталады, түпнұсқа өзгермейді.
- Үлгі өрістерін (ұйым атауы, күні, лауазым т.б.) автоматты толтыру.
- Үлгілер қазақ және орыс тілдерінде.
- Қолжетімділік деңгейі: `public` (барлық тіркелгендерге) және `employee` (тек қызметкерлерге).
- Үлгілерді тек әкімші қосады, өзгертеді, архивтейді; үлгі нұсқалары жүргізіледі.

### 5.7. Құжатты редакциялау

- Редактор тек авторизацияланған пайдаланушыға қолжетімді; қонақ тек оқу және талдау режимінде жұмыс істейді.
- Редактор тармақтық нумерацияны (1.1, 2.3 т.б.) сақтайды, бұл Source Trace үшін міндетті.
- Әр сақтау жаңа нұсқа (`document_versions`) жасайды, ешбір нұсқа үстінен жазылмайды.
- Автосақтау (30 секунд сайын) және қолмен сақтау.
- Екі нұсқаны қатар салыстыру (diff): өзгерген, қосылған, жойылған тармақтар белгіленеді.
- Нұсқаны қалпына келтіру (rollback) жаңа нұсқа жасайды.
- Бір құжатты екі адам бір мезгілде өңдесе, жүйе ескертеді (optimistic locking).
- Құжатты PDF және DOCX форматында жүктеп алу.

### 5.8. Әрекеттер тарихы (History)

Пайдаланушы аккаунтқа кіргеннен кейін бұрын жасаған немесе өзгерткен құжаттар тарихын көреді.

- Құжаттар тізімі: атауы, түрі, құрылған және соңғы өзгерген күні, нұсқалар саны, статусы.
- Әр құжат бойынша нұсқалар тізімі: нұсқа нөмірі, авторы, күні, өзгерістің қысқаша сипаттамасы.
- Талдаулар тарихы: қай екі құжат салыстырылды, қашан, нәтижесі қандай. Сақталған нәтиже ЖИ-ді қайта шақырмай ашылады.
- Үлгі бойынша жасалған құжаттарда бастапқы үлгі көрсетіледі.
- Іздеу, сүзгі (күні, түрі, статусы), сұрыптау.
- Тарихтағы құжатты қайта ашу, жалғастыру, көшірме жасау, экспорттау, жою (қоқыс жәшігі, 30 күн).
- Пайдаланушы тек өз тарихын көреді; әкімші жүйелік журналды толық көреді.

## 6. Дерекқор

Тіркелген пайдаланушылардың деректері, құжаттары және тарихы тұрақты дерекқорда сақталады. Ұсынылатын технология: PostgreSQL (MVP үшін SQLite болады).

- Қонақтың деректері дерекқорға жазылмайды, ол уақытша жадта өңделіп, талдаудан кейін жойылады.
- Дерекқордың күнделікті резервтік көшірмесі жасалады.
- Пайдаланушы өз аккаунтын және деректерін жоюды сұрай алады.
- Құпия құжат мазмұны дерекқорда шифрланған түрде сақталады.
- Барлық сұраулар параметрленген (ORM), SQL-инъекциядан қорғау қамтамасыз етіледі.

## 8. Функционалды емес талаптар

### 8.1. Қауіпсіздік және деректер құпиялылығы

- Frontend бөлігінде API кілттерін сақтауға қатаң тыйым салынады; кілттер тек серверде.
- RBAC әр сұраныс бойынша серверде тексеріледі; рөл, рұқсат және иелік тексерісі frontend-ке сүйенбейді.
- Қонақтың сессия күйі (Session State) уақытша жадта сақталады; тіркелгендердің деректері дерекқорда.
- CSV файлдарын экспорттау кезінде формула инъекцияларынан қорғау (Formula Prefix Protection).
- HTTPS міндетті; CSRF, XSS және SQL-инъекциядан қорғау.
- Маңызды әрекеттер (кіру, құжатты өзгерту, жою, рөлді өзгерту) `activity_log` кестесіне жазылады.
- Құжаттарды сыртқы ЖИ API-ге жіберу компанияның құпиялылық саясатына сәйкес болуы тиіс; құпия құжаттар үшін жеке (on-premise) модельді қолдану мүмкіндігі қарастырылады.

### 8.2. Өнімділік

- Сыртқы ЖИ сұрауларының ең жоғары таймауты (Timeout) — 120 секунд.
- Жауап беру уақыты созылған жағдайда талдауды тоқтату батырмасы (Abort Controller) болуы тиіс.
- Бір пайдаланушыға ЖИ сұраулары бойынша квота қойылады, әкімші оны өзгерте алады.

### 8.3. Интерфейс (UI/UX)

- Адаптивті дизайн (Desktop/Mobile).
- Жүйелік қаріптерге және оффлайн режиміне қолдау көрсету (авторизация және ЖИ талдауынан басқа функциялар үшін).
- Қазақ және орыс интерфейс тілдері.

## 9. Қабылдау тестінің сценарийі (Acceptance Criteria)

1. Екі түрлі редакциядағы құжат (мысалы: №8 және №9 редакциялары) жүктелгенде:
   - Жүйе жаңадан құрылған құрылымдарды (мысалы: ДИТААД, ДОА) жүйелі түрде көрсете алуы керек.
   - Ескі және жаңа тармақтарды (мысалы, 3.4, 3.5, 5.3.2) қатар ашып, семантикалық айырмашылықты көрсете алуы қажет.
2. Талдау аяқталған соң сараптамалық есеп PDF/CSV форматында дұрыс жүктелуі тиіс.
3. Қонақ құжаттарды жүктеп, талдау нәтижесін көре алады; нәтиже дерекқорға сақталмайды. Экспорттау, сақтау және редакциялау кезінде жүйе кіруді ұсынады.
4. Қонақ API арқылы тікелей `PUT /api/documents/:id` шақырса, сервер `401` қайтарады.
5. Пайдаланушы тіркеледі, email растайды және жүйеге кіреді; оның деректері дерекқорда, құпиясөзі хэш түрінде сақталады.
6. Пайдаланушы басқа пайдаланушының құжаты мен тарихын көре алмайды (`404`). Рөлге рұқсат етілмеген әрекет `403` қайтарады.
7. Қызметкер үлгілер каталогынан үлгі таңдап, құжат жасайды және өңдейді; әр сақтау жаңа нұсқа жасайды.
8. Қызметкер емес пайдаланушыға `employee` деңгейіндегі үлгілер көрінбейді және API арқылы қолжетімсіз.
9. Пайдаланушы шығып, қайта кіргеннен кейін «Тарих» бөлімінде бұрынғы құжаттарын, нұсқаларын және талдауларын көреді, кез келген нұсқаны қайта аша алады.
10. Әкімші рөлді өзгерткенде немесе пайдаланушыны бұғаттағанда, өзгеріс 60 секундтан кешікпей қолданылады.
11. Әкімші үлгі қосады, өзгертеді, архивтейді, журналды қарайды.
